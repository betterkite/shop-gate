# v0.1 目标架构与核算约定

这是待落地设计，不是当前实现说明。范围与 [功能矩阵](feature-matrix.md) 对齐；实现时补实际代码/API 和验证 revision。

## 分层与数据流

| 层 | 职责 | 禁止事项 |
| --- | --- | --- |
| Next.js业务页面 | 八页统一主题、范围、完整表格、详情与助手 | 从当前页重算总指标；模型重写页面源码 |
| 服务端业务网关 | 验证已有会话、工作空间成员与能力权限，传递可信作用域 | 信任浏览器提交的user/workspace身份；暴露服务凭据 |
| commerce-data经营领域 | 指标目录、账本查询、统一聚合、导入和操作预览/确认 | 接收模型任意SQL；行为事件乘价格作成交 |
| PostgreSQL经营账本 | 正式交易、历史快照、费用分摊、版本、审计、幂等记录 | 混用SQLite正式账本；自动覆盖旧数据 |
| Redis/查询缓存 | 按授权作用域、数据版本、标准化查询缓存 | 跨工作空间复用结果；过期数据冒充当前 |
| PI Agent治理与分析工具 | 页面上下文→问题/步骤→受控查询→证据答案/表格/图表 | 默认生成通用工作空间；建议自动改账本 |

复用 Next.js、现有认证/会话、PI模型与执行治理基础；新增经营账本和业务域，不复制参考项目 Vite/SQLite 单演示身份架构。旧行为分析只能标为行为数据，不能迁移成订单事实。

## 正式账本

建议在独立经营 schema 中维护工作空间、数据集、版本、平台、店铺、商品、标准规格、平台映射、汇率、订单、订单行、退款事件、成本版本、付款成本快照、费用、分摊、目标、保存视图、导入批次、操作预览与审计。每个外键必须约束同工作空间/数据集，不只在UI过滤。

数据版本是一次分析的一致性边界。查询、报表、导出和助手回合都返回使用的版本与截止时间；导入/确认操作在一个事务内更新事实、版本和审计。长期导出/重算使用可跟踪作业，不在浏览器等待期间隐式重做。

## 核算规则

1. 付款商品收入来自订单行优惠后的原币实收；汇率有来源和日期，人民币金额精确核算。付款订单数按业务订单去重，不按订单行计数。
2. 净销售收入 = 付款商品收入 − 已完成商品退款。经营贡献利润扣有效商品成本及平台、包装、商家物流、广告等实际费用；不包含未接入的人员/房租等固定支出。
3. 成本按付款时间匹配店铺规格、平台规格、基础规格，优先使用更具体层级，三层不相加。历史快照保存成本版本、数量/换算、来源、汇率与核算状态。
4. 仅退款保留成本；实际可回收退货按原快照冲回相应数量。部分/累计退款不得超原交易约束，费用调整只依据显式账本记录。
5. 费用先在完整来源范围确定分摊，再按查询过滤；采用确定性精确余数分配。不可归属商品的费用在整体/店铺仍承担，单独显示，不假分配到某商品。
6. 缺映射、成本或汇率不按0/1补齐。区分已核算金额、未知范围与覆盖率；修复后须显式预览和确认历史重算。
7. 金额最小单位为分，成本/数量4位、汇率8位；持久化使用确定精度整数或 PostgreSQL 精确numeric，领域使用Decimal；API金额为十进制字符串。前端浮点只用于绘图，不承担账本计算。
8. 付款归属与退款发生口径分别描述；事件口径无合适收入分母时不展示误导退款率。分组率从汇总分子/分母计算，不平均单行比率。零/负比较基数说明不可比。
9. 当前成本查询、历史加权成本、成本变更记录是三个不同结果。标准数据往返导出与供表格阅读的报表导出也是两个不同契约。

## 授权与操作协议

权限必须从现有服务端会话和成员关系得到，服务间授权至少绑定工作空间/数据集、操作能力、有效期及数据版本。模型只获得最小范围工具结果，不拿到数据库/模型密钥。

所有正式变更采用「规范化请求→只读预览→用户明确确认→重新验证权限/版本/过期/幂等→事务提交→版本/缓存失效→审计」。同幂等键不同内容拒绝，旧预览不能覆盖新数据，批次失败全部回滚。仅查看/模拟不改变版本和历史快照。

## Agent输出协议

事实问题输出答案及来源；排名给全量可分页表格；趋势/比较补相关图表；明确持续查看才保存专题分析。组件未覆盖但数据足够时继续问答/表格。只有真实缺数据或必要歧义才最少澄清，不让用户重复输入已在页面的范围或内部ID。

每轮固定页面模块、数据集/版本、日期、平台、店铺、商品、类目和选中对象，并记录查询参数、指标定义、证据与执行状态。多轮继承对象；切换空间/数据集隔离上下文。模型不可用不影响确定性BI。

旧通用 Data Agent 与历史成果不会在R0立即删除，但不再作为新经营页面的计算依赖。旧问答降级测试与授权/审批/预算/取消能力按现有事项逐项承接并重新验收。
